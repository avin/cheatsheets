# Организация CSS и инструменты

Эта глава остаётся в Markdown: здесь важнее решения о структуре проекта, команды и проверка результата, чем отдельные CSS-правила.

## Организация файлов и слоёв

Для приложения с несколькими экранами можно начать с такой структуры:

```text
styles/
├── index.css          # порядок @layer и импорты
├── tokens.css         # цвета, интервалы, типографика
├── reset.css          # box-sizing и базовый сброс
├── base.css           # типографика и базовые элементы
├── components/        # кнопка, карточка, поле формы
└── utilities.css      # точечные вспомогательные классы
```

В `index.css` порядок слоёв объявляют до импортов:

```css
@layer reset, base, components, utilities;
@import url("./reset.css") layer(reset);
@import url("./tokens.css") layer(base);
@import url("./base.css") layer(base);
@import url("./components/button.css") layer(components);
@import url("./utilities.css") layer(utilities);
```

- **Когда применять**: несколько разработчиков правят общие стили, а порядок подключения уже влияет на результат.
- **Плюсы**: легче найти правило и объяснить приоритет без повышения специфичности.
- **Риск**: обычные правила вне слоёв имеют приоритет над обычными правилами внутри них. Проверьте CSS сторонних библиотек и договоритесь, где живут исключения.
- Называйте классы по назначению компонента (`.card__title`, `.card--compact`); не привязывайте стили к случайной вложенности DOM.

## Проверка стиля в проекте

Установите линтер в проект и запускайте его одинаково локально и в CI:

```bash
npm install --save-dev stylelint stylelint-config-standard
npx stylelint "styles/**/*.css"
```

Минимальный `stylelint.config.mjs`:

```js
export default {
  extends: ["stylelint-config-standard"],
};
```

- **Когда применять**: правила дополняют друг друга и ошибки в CSS сложно заметить при просмотре diff.
- **Плюсы**: ранняя проверка синтаксиса и единый стиль записи.
- **Риск**: конфигурация может требовать настройки под используемые функции CSS и сборщик; исправляйте конкретные правила вместо массового отключения линтера.

## Проверка в браузере

1. В DevTools откройте **Computed** и **Styles**: найдите победившее правило, слой и переопределённые объявления.
2. Проверьте узкий экран, масштаб 200%, длинный текст, клавиатурный фокус и обе цветовые темы.
3. В панелях **Layout** и **Performance** проверьте сетку, переполнение и дорогие анимации.
4. Отключите загрузку веб-шрифта: текст должен остаться читаемым на запасном шрифте.

## Производительность и типичные ошибки

- Загружайте только нужные начертания шрифта; для локального файла используйте WOFF2 и `font-display` с подходящей политикой.
- Изображениям задавайте размеры в HTML, чтобы уменьшить сдвиги раскладки; в CSS используйте `max-width: 100%` и подходящий `object-fit`.
- Не добавляйте `will-change` ко всем элементам. Сначала найдите проблему в профиле браузера.
- Не ставьте `overflow: hidden` на весь макет ради устранения горизонтальной прокрутки: найдите элемент, который её создаёт.
- Проверяйте `:focus-visible`, контраст и `prefers-reduced-motion`; красивый hover не заменяет клавиатурное состояние.
